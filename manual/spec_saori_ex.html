SAORI over DirectSSTP

参考：SAORI/1.0（外部サイト）

SAORI/1.0の要求を、DLLのrequest関数ではなくDirect SSTPでベースウェアに送り、ベースウェアに内蔵された機能（内蔵モジュール）をSAORIとして呼び出すための拡張規格です。[SSP 2.9.13]
SHIORIから見ると「DLLを置かずに使えるSAORI」になります。ハッシュ・暗号・乱数・日時の計算など、これまでゴーストごとにDLLを同梱していた機能をベースウェアが提供します。
このページの前半（SAORI/1.0の概要～送信側の手順）はベースウェアに依存しない規格、後半（内蔵モジュール）はSSPが内蔵しているモジュールの説明です。

SAORI/1.0の概要

SAORI/1.0の正しい定義は原典（外部サイト）を参照してください。ここではこのページを読むのに必要な部分だけを簡単にまとめます。

要求

EXECUTE SAORI/1.0
Charset: UTF-8
Sender: 呼び出し元の名前
SecurityLevel: Local
Argument0: 1つ目の引数
Argument1: 2つ目の引数

改行はCR+LF、空行で終わります。引数はArgument0から番号順に並べます。値が空の引数も、その位置の引数として数えます。
Charsetは要求の文字コードで、応答も同じ文字コードで返ります。
機能の有無の確認にはGET Version SAORI/1.0を使います。

応答

SAORI/1.0 200 OK
Charset: UTF-8
Result: 結果
Value0: 複数の値を返すときの1つ目
200 OK
成功。Resultが結果。複数の値を返すときはValue0、Value1…にも入る。
204 No Content
成功したが、返す値が無い（結果が空文字列）。
400 Bad Request
呼び出し方の誤り。
500 Internal Server Error
処理の失敗。

SAORI over DirectSSTP

送り方

Direct SSTPと同じくWM_COPYDATA（dwData = 9801）を使い、lpDataにSSTPの要求の代わりにSAORI/1.0の要求を入れて、自分のゴーストの窓（FMOのhwnd）へ送ります。
窓・WM_COPYDATAの扱い（SendMessage系で送る、cbDataなど）はDirect SSTPと同じです。

EXECUTE SAORI/1.0
Module: internal_crypto
Charset: UTF-8
Sender: YAYA
SecurityLevel: Local
HWnd: 1234
Argument0: Digest
Argument1: sha256
Argument2: abc
Module
【必須】呼び出すモジュールの名前。DLL名から.dllを除いた形で書く（例：internal_crypto、string）。大文字小文字は区別しない。
無ければ400（ErrorDescription: invalid parameter）、知らないモジュールなら400（ErrorDescription: unknown module）。
HWnd
返事を受ける窓。省略時はWM_COPYDATAのwParamの窓（Direct SSTPのSSTPと同じ規則）。
Charset
要求の文字コード。応答も同じ文字コードで返る。
SecurityLevel
Direct SSTPでは常にLocalとして扱う（ヘッダの値は見ない）。
Sender
呼び出し元の名前。ベースウェアは使わない。
Argument[n]
引数。SAORI/1.0と同じ。

応答の受け取り

応答はHWnd（またはwParam）の窓へ、WM_COPYDATA（dwData = 9801）で返ります。内容はSAORI/で始まるSAORI/1.0の応答です。
ベースウェアは要求の処理中に返事を送るので、送信側のSendMessageが戻る前に返事が届きます。

受け付ける経路

SAORI over DirectSSTPはDirect SSTPだけで受け付けます。
ソケットのSSTPやSSTP over HTTPでSAORI/1.0の要求を送ると、SAORI/1.0 400 Bad RequestとErrorDescription: direct sstp onlyが返ります（SSTP over HTTPでは、HTTPの200の本文としてこの応答が返ります）。
SAORIの要求はSSTPログに記録されません。

呼び出し元のゴースト

ゴーストの窓へ送った場合は、そのゴーストが呼び出し元になります。
ベースウェアの主窓へ送ったときなど、呼び出し元のゴーストが分からない場合は「ゴーストなし」として扱います（Direct SSTPのSSTPのように表示中のゴーストを代わりに当てることはしません）。 ゴーストを使わない処理は普通に動き、ゴーストに依存する処理（結果をイベントで届ける非同期の呼び出し、ゴーストのフォルダを基準にした相対パスなど）は400（ErrorDescription: ghost required）になります。
ReceiverGhostName / ReceiverGhostHWndヘッダは見ません。

返事の取り違えを防ぐ

ベースウェアは、SAORI/（およびSSTP/）で始まる受信を返事とみなし、要求としては扱いません。

機能の判定

モジュールが使えるかどうかは、GET Version SAORI/1.0にModuleを付けて送って確かめます。使えればSAORI/1.0 200 OK（SSPではResult: SSP Internal）が返ります。
この拡張に対応していないSSP（2.9.12以前）はSAORI/1.0の要求をSSTPの要求として読み、SSTPのエラー（GET VersionにはSSTP/1.0 501 Not Implemented、EXECUTEにはSSTP/1.0 400 Bad Request）を返します。
送信側は「SAORI/1.0 200で始まる返事でなければ使えない」「返事が来なければ使えない」と判定してください。

ErrorDescription

失敗したときは、応答にErrorDescriptionヘッダで失敗理由（固定の英語の文字列）が付きます。SAORI/1.0の原典には無いヘッダで、SHIORI/3.0の同名のヘッダにならっています。
どのモジュールでも使うものは次のとおりです。ほかは各モジュールの説明を参照してください。

direct sstp only
400。Direct SSTP以外の経路で送った。
unknown module
400。Moduleのモジュールが無い。
unknown function
400。関数名（Argument0）がモジュールに無い。
ghost required
400。呼び出し元のゴーストが分からないのに、ゴーストに依存する処理を求めた。
invalid parameter
400。Moduleの欠け・引数の欠けや誤り。

互換モジュール（DLLのSAORIの互換）は、原作どおりErrorDescriptionの付かない400を返すことがあります。

ヘッダの値に書けないもの

SAORIのヘッダの値には、改行と、先頭・末尾の空白を書けません（カンマは書けます）。こうしたデータは、内蔵モジュールでは--data-in=base64などの形式を使って渡してください。

非同期の呼び出し

内蔵モジュール（名前がinternal_で始まるもの）の関数は、オプション--async=識別子を付けると非同期で動きます。要求を受け付けると、応答はすぐに204で返り、結果はあとで呼び出し元のゴーストへイベントで届きます。
ゴーストなしの呼び出しでは使えません（400 ghost required）。識別子が空なら400（invalid parameter）です。
時間のかかる処理（大きなファイルのハッシュ、パスワードのハッシュ、鍵の導出、RSAの鍵ペアの生成など）には--asyncを使ってください。
同時に動く非同期の呼び出しは、SSPではCPUの数ほど（2～4）までです。それを超えた分は、前のものが終わるまで順番を待ちます。

結果を届けるイベント

イベント名
識別子がOnで始まれば、成功時はその名前、失敗時は「識別子＋Failure」。
そうでなければ、成功時はOnInternalSaoriComplete、失敗時はOnInternalSaoriFailure。
成功時のReference
Reference0＝識別子、Reference1＝結果（同期の呼び出しのResult）、Reference2＝モジュール名、Reference3＝関数名、Reference4以降＝Value0以降。
失敗時のReference
Reference0＝識別子、Reference1＝失敗理由（同期の呼び出しのErrorDescriptionと同じ文字列）、Reference2＝モジュール名、Reference3＝関数名。

引数の数やオプションの名前の誤りは、受付の時点で400になります。引数の中身の誤り（読めない16進など）は、失敗のイベントで届きます。
結果が届く前に呼び出し元のゴーストが終了した場合（SHIORIの再読み込みを含む）、結果は届きません。

送信側の手順

SHIORIなどの送信側は、次の手順でSAORI over DirectSSTPを使います。

  1. FMOなどから、自分のゴーストの窓（hwnd）を得る。
  2. 返事を受ける窓を用意する。
  3. SAORI/1.0の要求を組み立てて、ModuleとHWnd（返事を受ける窓）を付ける。
  4. ゴーストの窓へWM_COPYDATA（dwData = 9801）をSendMessage系の関数で送る。
  5. 返事を受ける窓にWM_COPYDATA（dwData = 9801）で届いた、SAORI/で始まるデータを応答として読む。

使えるかどうかは、最初にGET Versionで確かめてください。

内蔵モジュールの共通規約

SSPが内蔵している、名前がinternal_で始まるモジュールの共通の決まりです。（同じ名前のSAORI DLLと衝突しないように、internal_で始まる名前にしています。）
これらのモジュールはDirect SSTPからだけ呼べます。DLLとしてloadすることはできません。

関数と引数

Argument0が関数名（大文字小文字は区別しない）、Argument1以降がその関数の引数です。知らない関数名は400（unknown function）です。
引数は、関数ごとに決まった数の位置引数と、その後ろに並べるオプション（--名前=値）からなります。

  • 位置引数の位置にある値は、--で始まっていてもオプションとしては読まず、データとして扱います。
  • オプションは位置引数より後ろにだけ書けます。省略できる位置引数を飛ばしてオプションを書くときは、空の引数を置いてください。
  • オプションの名前は大文字小文字を区別しません。同じ名前を2回書くと後のものが有効です。
  • 位置引数より後ろにある--で始まらない値、関数が受け付けないオプションは400（invalid parameter）です。
  • どの関数も--async=識別子を受け付けます。
Argument0: Digest
Argument1: sha256
Argument2: SGVsbG8=
Argument3: --data-in=base64
Argument4: --out=base64

バイト列の入力の形式

ハッシュなどはバイト列を扱いますが、SAORIで渡せるのは文字列です。バイト列を受け取る引数にはそれぞれ名前（data、key、password、salt、ciphertext、signature、a、bなど。各関数の説明を参照）があり、--名前-in=形式でその引数の読み方を変えられます。例：--key-in=hex、--data-in=base64。
オプションで渡すバイト列（--aad=、--iv=、--info=）も同じで、--aad-in=hexのように読み方を変えられます。

text
文字列を、--charset=の文字コード（既定はUTF-8）のバイト列にする。要求のCharsetではない（送り手の文字コードによらず、Web APIの署名などと同じ値になるように）。その文字コードで表せない文字があれば400（invalid encoding）。
hex
16進。大文字小文字はどちらでもよい。奇数桁・16進以外の文字は400（invalid encoding）。
base64 / base64url
パディング（=）はあってもなくてもよい。どちらの形式でも、base64とbase64urlの両方の文字（+ / - _）を読む。それ以外の文字・パディングの誤りは400（invalid encoding）。
base32
RFC 4648。大文字小文字・パディングの有無は問わない。不正な文字は400（invalid encoding）。
url
パーセントエンコードを戻したもの。+は空白に戻さない。%の後ろが16進2桁でなければ400（invalid encoding）。
file
値をファイルのパスとして、ファイルの中身を読む。internal_cryptoのDigest / HMACのdataだけで使える。
相対パスはゴーストのフォルダ（ghost/master）が基準。ゴーストなしの呼び出しで相対パスを渡すと400（ghost required）。ファイルが無ければ400（file not found）、途中で読めなくなったら500（file read failed）。

既定の形式は引数ごとに決まっています（各関数の説明を参照）。デコードした後のデータは1つの引数あたり8MBまで（too large）ですが、Direct SSTPの要求そのものが1MBまでなので、実際にはそれより小さくなります。fileは少しずつ読むので大きさの上限はありません。

バイト列の出力の形式

バイト列を返す関数は、--out=形式で結果の書き方を変えられます。既定の形式は関数ごとに決まっています。出力の既定の形式は、同じ名前の入力の既定の形式に合わせてあるので、出した値をそのまま別の関数に渡せます。

hex
16進（小文字）。
HEX
16進（大文字）。
base64
パディングあり。
base64url
パディングなし。
base32
RFC 4648。パディングあり。
url
RFC 3986の非予約文字（A-Z a-z 0-9 - . _ ~）以外をすべて%XX（大文字）にする。
text
--charset=の文字コード（既定はUTF-8）の文字列として返す。その文字コードとして正しく戻せないバイト列や、NUL・改行（SAORIのヘッダに書けない）を含むときは500（not text）。
応答は要求のCharsetの文字コードで返るので、そこで表せない文字は?に化けます。どんな文字でも受け取れるように、要求はCharset: UTF-8で送ってください。

--charset=には文字コードの名前（UTF-8、Shift_JIS、EUC-JPなど）を書きます。知らない名前やUTF-16は400（invalid parameter）です。

応答と失敗理由

成功すれば200でResultに結果が入ります。結果が空文字列のときは204です。真偽を返す関数は、200で1（真）または0（偽）を返します。「一致しない」などは失敗ではありません。
失敗時のErrorDescriptionには、共通のもののほかに次のものがあります。

unsupported algorithm
400。知らないアルゴリズム名。
invalid encoding
400。--名前-in=の形式として読めない。圧縮データが壊れている。
invalid key
400。鍵の長さがアルゴリズムに合わない。公開鍵暗号の鍵として読めない、鍵の種類が方式に合わない。
out of range
400。数値・日時が扱える範囲の外。
too large
400。データが大きすぎる。
file not found
400。--data-in=fileのファイルが無い。
not text
500。--out=textで文字列に戻せない。
file read failed
500。ファイルを途中で読めなくなった。
authentication failed
500。復号できない（暗号文の改ざん・鍵の違いなど）。JWTを検証できない。
expired / not yet valid
500。JWTの有効期限（exp）が切れている / 有効になる時刻（nbf）より前。
internal error
500。ベースウェア内部の想定外の失敗。

共通鍵暗号（Encrypt / Decrypt）

アルゴリズムは次のとおりです（名前のハイフン・アンダースコアの有無と大文字小文字は区別しない）。これ以外は400（unsupported algorithm）です。

aes-256-gcm（推奨） / aes-128-gcm / chacha20-poly1305
認証付き暗号。改ざんされた暗号文は復号できない。暗号文の形は「nonce（12バイト）＋暗号文＋認証タグ（16バイト）」。
aes-256-cbc / aes-128-cbc
PKCS#7のパディング。暗号文の形は「IV（16バイト）＋暗号文」。改ざんを検出できないので、ほかのシステムとやりとりするときだけ使うこと。
aes-256-ctr
暗号文の形は「IV（16バイト）＋暗号文」。改ざんを検出できない。

鍵（key）の長さは、アルゴリズムの鍵長ちょうど（AES-256とChaCha20は32バイト、AES-128は16バイト）でなければ400（invalid key）です。パスワードから鍵を作るときはDeriveKeyを通してください。
nonce / IVは、暗号化のたびに乱数で作って暗号文の先頭に付けます。--iv=（nonce / IVを指定する）と--pack=none（先頭に付けない）は、ほかのシステムがnonceを別に受け渡す場合のためだけのものです。同じ鍵で同じnonce / IVを2回使うと、GCM・ChaCha20-Poly1305・CTRは暗号として破れます（平文が漏れ、改ざんもできるようになる）。--iv=に固定の値を書いて使い回さないでください。

Argument2

オプション
--key-in= / --data-in= / --aad=（追加認証データ。認証付き暗号だけ。--aad-in=、既定の形式はtext） / --iv=（--iv-in=、既定の形式はhex） / --pack=none / --out=（既定はbase64） / --charset=

公開鍵暗号（GenerateKeyPair / Sign / Verify）

署名の方式は次のとおりです（名前のハイフン・アンダースコアの有無と大文字小文字は区別しない）。これ以外は400（unsupported algorithm）です。それぞれJWT（JWS）のalgのEdDSA / ES256 / RS256 / PS256と同じ署名になります。

ed25519
Ed25519（RFC 8032）。署名は64バイト。
es256
ECDSA（P-256）+ SHA-256。署名は64バイト（r‖s。JWSと同じ形で、DER形式ではない）。
rs256
RSA（RSASSA-PKCS1-v1_5）+ SHA-256。
ps256
RSA（RSASSA-PSS）+ SHA-256。MGF1もSHA-256、ソルトは32バイト（JWAのPS256と同じ）。

鍵は、1行のDERのbase64か、PEMで渡します。GenerateKeyPairは前者（秘密鍵はPKCS#8、公開鍵はSubjectPublicKeyInfo）を出力します。

RSAの鍵は2048～4096ビット、ECDSAの鍵はP-256だけです。読めない鍵・種類や大きさが方式に合わない鍵は400（invalid key）です。

秘密鍵は、必要ならProtectで包んで保存してください。

互換モジュール

SSPは、よく使われていた次のSAORI DLLの互換の機能を内蔵しています。ゴーストがこれらのDLLをloadすると、SSPはDLLを読まずに内蔵の機能に差し替えます（ファイル名で判定します）。
[SSP 2.9.13] これらはDirect SSTPからも、DLL名から.dllを除いた名前（Module: stringなど）で呼べます。引数と戻り値は原作のSAORIのままです。

houchi clipcopy textcopy saori_ip saori_cpuid mciaudio cpuusage httpc string hanayu

  • Direct SSTPにはload / unloadが無いので、ゴーストごとに状態を持つもの（mciaudio / httpc / string / hanayu）は、そのゴーストの最初の呼び出しで用意し、ゴーストの終了（SHIORIの再読み込みを含む）で捨てます。DLLとしてloadしたものとは状態を共有しません。
  • ゴーストなしの呼び出しでは、ゴーストに依存する処理（httpcの取得・保存とbg、hanayuのshow、mciaudioのload / play / loop / stop）は400（ghost required）になります。
  • houchiはloadしたときに働くものなので、Direct SSTPから呼んでも何も起きません。
  • Direct SSTPの要求はSSPの主スレッドで処理されるので、httpcの取得はbgを付けて行ってください（付けないと、取得の間SSPの画面が止まります）。
